# Bench tables

Generated by `node packages/verify/dist/cli.js bench index packages/verify/docs/bench` from the JSON tables in
`docs/bench/`. Do not edit this page: re-emit the table from its run with `node packages/verify/dist/cli.js bench emit`, then
regenerate. Every figure here sits inside a generated block that names the table it came from and that table's
sha256, so a reader can check a block against the JSON beside it. Commands on this page run from the repository root.

A table is emitted only against a prereg whose sha256 was recorded. `bench emit` reads the recorded chain
(the frozen hash, then every amendment), and refuses when no hash was recorded, when the prereg changed after its last
record, or when a recorded snapshot changed. A recorded hash proves which text was frozen. The tool checks that the
record exists, not when it was made: a record's time is the authors' own. Each table's **Stamp** line says what a
third party can show. Stamping began on 2026-10-05: a prereg frozen before then reads "unstamped (frozen before 2026-10-05)",
a later run with no proof reads NEEDS STAMP, and a stamp made after its run is shown as that, never as a stamp before it.

**The stamp rule, from 2026-10-05.** Every preregistration is to be stamped by a timestamp authority before its run. This tree does not meet the rule everywhere yet: the exceptions are listed below, after how a stamp is made.
A stamp is made with
`node packages/verify/dist/cli.js bench stamp <prereg> --tsa http://timestamp.digicert.com`
sends the file's sha256 and writes the authority's signed reply beside it as `<prereg>.tsr`. The table records the
stamp's time beside the run's time on its **Stamp** line, which the tool writes from the token and the run date, so a
stamp made after its run can only read "stamped after the run". A run made after stamping began whose stamp came later
also says so in a note on its first row.

Each table's evidence ships beside it. The folder `docs/bench/<id>/` holds the prereg byte for byte, every hash list
the prereg check reads, the run spec, the per-case results, and `run.json`, which says where each file came from.
`node packages/verify/dist/cli.js bench check packages/verify/docs/bench` re-emits every table from its folder and compares
byte for byte. That is a re-tally from the per-case results that ship, not a rerun: it shows the table is what its
results give, not that the results are what the run would give again. Preregs ship unedited so their sha256 can be
checked. Where one names a file path in the authors' working tree, its table says so.
Where a hash list or the prereg names a file the folder does not hold (a harness, raw data, a large per-case file), the
table lists it under "Hashed, not shipped" beside its sha256, with the reason. Where a hash-listed file ships in bytes
other than the recorded ones (a comment line that named a private folder was rewritten), the table lists it under
"Ships, edited" with both sha256s and the reason; the original does not ship, so a reader cannot check the difference.
The check refuses a hash-listed file that neither ships in those bytes nor is listed.
`node packages/verify/dist/cli.js bench emit packages/verify/docs/bench/<id>` re-emits one table from the files in its folder.
`bench check` exits 0 when everything holds, 1 on any DIFFERS, refusal or failure, and 4 when everything holds but a
table reads NEEDS STAMP (see the stamp rule above), or a preregistered run that has not run pins an engine, a rule or
source files this tree no longer builds (a STALE PINS line names each pin that moved; `--strict-pins` refuses instead).

**The AP stress rows.** The AP stress study is not a table (its numbers are under "Outside the rule"), but its banked
rows, 30 files in `bench/ap/results/` at the repository root, claim that a fresh run of `bench/ap/stress.ts` reproduces
them byte for byte. Each row carries `checker_sha256`, the sha256 over the AP pack's source files, with the engine version
and the AP ruleset. `bench check` compares every banked row with what this tree builds and fails when they differ, so an
AP change that was not re-banked cannot pass unseen. Each re-bank is dated in [`bench/ap-blind/STRESS-AMENDMENT-2026-10-05.md`](bench/ap-blind/STRESS-AMENDMENT-2026-10-05.md).
The files are named for five "holdout" seeds. They are fixed seeds, not a holdout: one re-bank followed a change to
the AP pack made with these seeds' results in view (the amendment says which), so they test reproduction, not
generalisation.

**Re-bank history, from that file.** The rows were re-banked 14 times over 12 amendments: 4 on 2026-10-05, 4 on 2026-10-06, 3 on 2026-10-13, 2 on 2026-10-14, 1 on 2026-10-20.
The last two: "Eleventh amendment, 2026-10-14: re-banked, digest only, after the verdict door held ap-threeway@0.3.0 to the line recompute"; "Twelfth amendment, 2026-10-20: re-banked, digest only, after ap-threeway@0.4.0 joined the pack as a selectable ruleset".
Typed text further down this page says the rows were re-banked thirteen times; the amendment file records 14 re-banks, the last on 2026-10-20. The file is the record, and the typed text is to be corrected to it.

Each row names its claim, its counts, a two-sided interval at the stated confidence by the named method (Wilson or
Clopper-Pearson), the bar as the prereg states it, and the verdict against that bar. A row with no preregistered bar is
descriptive and reads INSUFFICIENT. A row held to a bar written for another run, reused after the fact, has no verdict
of its own: its verdict cell reads "post-hoc" and names whose bar it is. Labels: blind, by the authors' records (by the
authors' own hash times, fetch logs and notes, the builder had not seen the data before the run; no third party has
confirmed that for any table, each blind table names the record it rests on, and the label says nothing about who
audited, which a table states separately), post-hoc (scored on data already seen), demo (a constructed demonstration),
regression (a re-run showing nothing moved), transcribed (typed from a report that left no machine-readable results).
Misses are listed in `MISSES.md`.

Scope: most tables test the document checks (invoices, e-invoices, legal quotations, a purchase log). The tables whose
ids start with `sci-` hold the same prereg-and-replay discipline to public science tables (galaxy rotation curves,
ocean floats, gravity inversions). They are here because the bench rule covers every table on this page, not because
the invoice checker reads galaxies. Numbers published outside the rule are listed under "Outside the rule", with the
reason for each.
The tables titled "Cold review" record defects found by cold readers: AI agents that had not worked on this tree, each
given a copy of it in a buyer's or a reviewer's role. They are run by the maintainers. They are not people, not customers
and not independent reviewers, and nothing they found is evidence of how the checks do on real documents.
